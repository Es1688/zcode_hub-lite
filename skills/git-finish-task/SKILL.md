# git-finish-task — стандартное закрытие задачи (lite)

Ключевой принцип: **коммит — рабочий шаг; merge в main и push — только с явного
разрешения пользователя**. Пользователь учится git — каждую команду сопровождай
строкой «что она делает и зачем».

## PRECONDITIONS

Проверь до любых действий; нарушение = остановись и доложи, не продолжай молча:

1. Ты НЕ на ветке `main` (если на main — сначала предложи создать `feature/<task>`
   скиллом `git-start-task`).
2. Контекст задачи существует: `.zcode/tasks/<id>.md`. Если нет — создай по шаблону
   `<ZCODE_DIR>/templates/task-context.template.md`, заполни и согласуй, потом продолжай.
3. Изменения понятны: `git status --short` и `git diff` просмотрены; ты можешь объяснить
   каждый файл пользователю.
4. В коммит не должны попасть: секреты (.env, *.key, токены), служебное
   `.zcode/plans/`, посторонние файлы пользователя.

## STEPS

1. Прогони quality-чеки из `.zcode/project.yaml` (`quality.test`, `quality.lint` — что
   задано). Инструменты не установлены — зафиксируй это в задаче (раздел «Итог») и
   продолжай только с явного согласия пользователя.
2. **Шаг чистоты истории**: посмотри `git log main..<ветка> --oneline`. Каждый коммит
   должен быть осмысленным и соответствовать формату Conventional Commits
   (`feat|fix|docs|refactor|test|chore: summary`, английский). Мусорные WIP-коммиты
   («fix fix», «asdf», «тест») в main не идут: прибери историю — `git commit --amend`
   для последнего коммита или мягкий сброс (`git reset --soft`) и новый осмысленный
   коммит. Интерактивный rebase не требуется. Поясни пользователю, зачем это:
   «история main — это дневник проекта, по нему ищут, когда что-то сломалось».
3. Обнови задачу: `Статус: done`, заполни раздел «Итог» (что сделано, отклонения
   от плана, известные долги).
4. Коммит: добавляй только целевые файлы (`git add <явные пути>`, никогда `-A` вслепую).
   Поясни: «add — это выбор блюд, commit — заказ: берётся только то, что выбрали».
5. Спроси разрешение на merge. Получив: `git switch main` → `git merge --no-ff
   feature/<task>` (обычный merge с merge-коммитом: история ветки сохраняется целиком,
   в точке слияния видно, что была отдельная задача) → `git branch -d feature/<task>`.
6. Push — только отдельное явное разрешение. Remote нет — предложи создать приватный
   репозиторий (имя — из `project.yaml: name`).

## VALIDATION

- `git status --short` после коммита: чисто, или остался только осознанный WIP
  (перечисли его пользователю явно).
- `git log -1 --format=%s`: conventional-формат, английский.
- После merge: `git log --oneline -3` показывает merge-коммит.

## OUTPUT

- SHA коммита, текущая ветка, состояние main после merge.
- Что ждёт от пользователя (merge? push?) — если что-то не сделано из-за гейта.

## POSTCONDITIONS

- Ни merge в main, ни push не выполняются без явного «да» в этом диалоге.
- Задача в `.zcode/tasks/` закрыта (статус done, итог заполнен) и закоммичена.
